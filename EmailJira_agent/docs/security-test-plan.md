# EmailJira security test plan

Version 0.1.0 · 2026-10-22 · Status: planned, no security tests executed. Derived from [threat model](threat-model.md), [requirements](requirements.md), [verification criteria](verification-criteria.md) and [test strategy](test-strategy.md).

## Authorization, environment and evidence

Use synthetic sanitized inputs and isolated stores by default. Real provider checks require explicitly selected owned test resources and enabled live checks; never target third-party accounts. No live sending before the Phase 5 gate, explicit enablement and exact-message approval. Local attack strings are data, not commands to execute. Fault injection and fakes live only in tests/evaluation tooling. Use real Windows/SQLite where platform/persistence is the subject. Capture forbidden as well as expected side effects.

Each matrix row is a concrete security test condition with variants; implement named cases before the dependent feature is accepted. Each case must record initial state, source/actor/version, actions, observed requests, final local/remote state and sanitized evidence. Every expected result must pass; missing observation is Blocked/Fail, not assumed safe. Derived pytest IDs are linked at implementation time; existing detailed TC-P1 cases are reused rather than duplicated.

## Gate bundles

- **Phase 1 foundation:** applicable SEC-TC-013–016,020,023–024 portions plus TC-P1 cases, locked checks and actual Windows evidence. No model/API boundary claim from this subset.
- **Before first live Jira write:** SEC-TC-001–003,010,014,019 applicable controls; verify actual permissions/allowlist/correlation and distinguish provider writes from human decisions.
- **Before unattended model-driven business writes:** SEC-TC-021 and frozen EVAL-01 thresholds, plus deterministic policy checks. Controlled Phase 2 feasibility writes do not imply unattended enablement.
- **Before live sending:** SEC-TC-004–009,011,014,018–019 and actual current approval/execution checks; explicit user enablement remains required. Any uncertain or stale decision blocks.
- **Before operational release:** all applicable cases including restored-backup replay, notifications/rendering and full agreed adversarial types. Full offline/live/model/performance evidence and human walkthrough reviewed separately.

## Findings and maintenance

Developer fixes defects with regression tests; human reviews sensitive boundaries. Applicable exploitable vulnerabilities or failed mandatory acceptance block the relevant gate/release. Inconclusive scans, unavailable provider evidence, or unexecuted Windows tests cannot be marked passed. Record nonapplicable findings/exclusions with rationale and affected scope. Reassess after scope/token permissions, model/dependency, approval/payload, migration/restore or destination changes. Tests reduce risk but do not prove universal resistance or replace the threat model.
